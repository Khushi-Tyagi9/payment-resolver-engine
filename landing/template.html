The problem

A gap Razorpay can't see

Razorpay reconciles the bank and the gateway. It has no visibility into whether your own order table ever caught up.

This isn't hypothetical. In a documented WooCommerce Razorpay plugin bug, a successful renewal payment left the order marked pending even though Razorpay had confirmed it succeeded — the webhook fired correctly, but the store's own order table was never updated. Razorpay's records were right. The merchant's records were wrong. Nothing caught it until a customer complained.

Under the hood

The method, step by step

Every audit_log row traces back to this exact rule set. Nothing is inferred, nothing is guessed.

01

Correlate before comparing anything

The engine checks whether razorpay_payment_id maps to exactly one order_id and one amount across the whole batch. If a payment id resolves to conflicting orders or amounts, the record is marked CORRELATION_FAILED and skipped — it is never compared against data it doesn't actually belong to.

02

Catch reversals before they're mistaken for a match

If the event type is SETTLEMENT_REVERSED and this order was already resolved earlier in the same batch, it's routed straight to DISPUTED — regardless of what the status fields say. This check runs before the status compare, so a reversal can never be silently absorbed into "verified in sync."

03

Fall back to the LLM only for what Python can't classify

If razorpay_status isn't in the deterministic lookup table, the engine makes its one and only LLM call: Groq proposes a category for the unmapped code. That proposal is logged as UNCONFIRMED and never triggers an action on its own — it's a suggestion for a human to review, not an automatic outcome.

04

Compare with a direction, not a guess

Once correlation, the reversal check, and the unmapped check are all clear, the two statuses are compared. The direction of the mismatch matters more than the mismatch itself — the table below shows exactly which combinations auto-correct and which only ever get flagged.

05

Log exactly once, no matter how many times it runs

record_id is a primary key on audit_log. Re-running the pipeline against an already-processed batch can't create duplicate rows — every record is claimed and written exactly once.
